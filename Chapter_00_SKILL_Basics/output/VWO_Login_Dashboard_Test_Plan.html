1. Objective

The objective of this test plan is to verify that the VWO login experience provides secure and reliable access to the VWO platform while meeting the functional, usability, accessibility, performance, integration, and compliance requirements stated in the PRD.

Testing will cover the login journey for new and returning users, authentication error recovery, and the explicitly described page and security requirements. The plan also defines the test approach, environments, execution gates, and deliverables.

2. Scope

In scope

  • Email and password login, input validation, authentication feedback, loading state, and successful transition to the VWO dashboard.
  • Remember Me behavior and secure session creation, persistence, timeout, and termination, subject to approved session rules.
  • Forgot-password and email recovery flow, including reset-token behavior and password requirement enforcement.
  • Optional multi-factor authentication, enterprise SSO (including SAML and OAuth), and social sign-in with Google or Microsoft, if delivered in the release under test.
  • Registration/free-trial path, product announcement banner, and Light/Dark Mode options described in the current-state requirements.
  • Responsive layout, keyboard and screen-reader interaction, clickable labels, contrast, and WCAG 2.1 AA verification.
  • HTTPS and authentication-data/session protections; rate limiting and handling of repeated failed login attempts.
  • Login success/failure analytics, support entry points, and integration with the core VWO platform.
  • Page-load performance, concurrent login behavior, global/geographic behavior where environments are available, and regression after changes.
  • GDPR/CCPA data-handling expectations and enterprise audit requirements to the extent that acceptance criteria and test evidence are made available.

Out of scope

  • Post-login experimentation, personalization, analytics, or other VWO product functionality beyond verifying the handoff and access to the user’s dashboard.
  • Implementation or infrastructure design for authentication providers, CDN, multi-region deployment, and platform auto-scaling.
  • Biometric authentication, adaptive authentication, progressive web app behavior, and future personalization/A-B test enhancements, unless explicitly included in the release.
  • Independent certification of legal or regulatory compliance; QA will validate agreed product behaviors and supplied compliance criteria.
Scope note: MFA, SSO, social login, dark mode, high-contrast mode, and several recovery options are described as optional or capability-level requirements. Their release inclusion and exact expected behavior must be confirmed before execution.

3. Inclusions and test design

Test scenarios and cases will be derived from the approved requirements and acceptance criteria. Applicable test design techniques follow the test-plan skill.

  • Equivalence class partitioning: valid and invalid email/password inputs, credentials, and user/session states.
  • Boundary value analysis: input length and password policy limits once those limits are specified; session timeout boundaries and rate-limit thresholds once configured values are supplied.
  • Decision table testing: combinations of credential validity, Remember Me selection, MFA/SSO requirement, account state, and authentication outcome.
  • State transition testing: login form, submission/loading, success, failure, recovery, MFA, and session lifecycle transitions.
  • Use-case testing: new-user registration path, returning-user login, password recovery, and enterprise sign-in where enabled.
  • Error guessing and exploratory testing: malformed input, repeated submissions, interruptions, browser back/refresh, network changes, and recovery from service errors.

4. Test strategy

  1. Requirement analysis: review the PRD, clarify open behaviors and measurable acceptance criteria, and map requirements to scenarios.
  2. Shift-left preparation: review designs, field rules, authentication/session policies, integration contracts, and accessibility expectations before a stable build is available.
  3. Smoke testing: verify the login page loads, the principal controls render, and a basic authentication path is available. Reject the build for in-depth testing if smoke testing fails.
  4. Functional and end-to-end testing: execute approved scenarios for successful login, failure handling, recovery, new-user path, and dashboard transition.
  5. Non-functional testing: assess security, accessibility, responsive behavior, performance, browser/device compatibility, and concurrency against agreed criteria.
  6. Defect retesting and regression: retest fixes and rerun impacted and critical flows; repeat test cycles until exit criteria are met or risks are formally accepted.
  7. Exploratory testing: explore likely interruption, edge, usability, and recovery conditions alongside scripted execution.

Multiple test resources may execute against supported environments simultaneously after environment access, test accounts, and data isolation are arranged. Test execution should avoid real user accounts and production authentication unless explicitly authorized.

7. Entry and exit criteria

Requirement analysis

Entry: QA receives the PRD and available designs/technical details.
Exit: requirements are understood, testable, mapped to coverage, and blocking questions have owners or agreed decisions.

Test design and readiness

Entry: scope and requirements are available.
Exit: scenarios and test cases are documented and approved; environment, test accounts, test data, and dependencies are ready.

Test execution

Entry: application build is available in the agreed test environment; smoke test passes; test cases are approved; access and data are ready.
Exit: planned tests have results; defects are reported and triaged; critical fixes are retested; residual risks are documented. Release thresholds for pass rate and open defects are TBD and require stakeholder approval.

Test closure

Entry: test and defect reports are available and execution is complete or formally stopped.
Exit: test summary is submitted, unresolved defects/risks are recorded, and required stakeholder sign-off is captured.

8. Test execution

  • Run a focused smoke suite on each candidate build before full execution.
  • Execute test cases across the approved environment/browser/device matrix; record build, environment, test data reference, result, and evidence.
  • Prioritize P0 authentication, session, and security checks, followed by P1 user journeys, responsive/accessibility, and release-enabled integrations.
  • Mark cases blocked when a dependency, requirement, account, or environment is unavailable; report the blocker rather than treating it as a pass.
  • On failure, capture reproducible steps and relevant sanitized evidence, raise a defect, and link it to the requirement and test case.
  • Retest the fix and execute regression coverage based on change impact. Repeat cycles until agreed exit criteria are met.

Key end-to-end journeys

  1. Returning user enters valid email and password, receives processing feedback, and reaches the personalized VWO dashboard.
  2. User submits invalid or incomplete credentials and receives clear, actionable feedback without sensitive information being exposed.
  3. User selects or clears Remember Me and verifies the resulting persistence behavior against the approved session policy.
  4. User requests password recovery, follows the email reset flow, sets an allowed password, and returns to login.
  5. New user follows the free-trial registration link; destination and navigation behave as specified.
  6. Enabled enterprise/social/MFA sign-in completes, fails, or is cancelled and returns the user to an understandable and secure state.

9. Defect reporting procedure

Log deviations from approved requirements, broken user journeys, usability/accessibility barriers, security/privacy concerns, and technical errors in the project-approved defect tracker. The specific tracker and workflow are TBD.

Minimum defect information

  • Summary, environment/build, browser/device, severity and priority.
  • Preconditions, sanitized test-account reference, reproducible steps, expected result, and actual result.
  • Evidence such as screenshot, timestamp, or sanitized logs; do not attach passwords, reset tokens, session cookies, or other secrets.
  • Related requirement, test case, and any workaround or release impact.

QA reports and triages defects with the responsible product and engineering stakeholders. A daily end-of-day defect status update follows the process in the test-plan skill; recipients, channel, and severity definitions are to be confirmed.

Two-sprint duration has no dates, staffing, or scope-based capacity estimate.Agree sprint calendar, resource allocation, dependencies, and test milestones with the project team.
Performance and scale goals lack workload profiles, geographic locations, and concurrency targets.Define representative load, measurement method, and acceptance thresholds before load execution.
External identity, email, analytics, or support integrations may be unavailable or unstable.Arrange test tenants/stubs, integration contacts, and a fallback test window; record any resulting coverage limitation.
Testing real credentials or tokens could expose sensitive data.Use approved test accounts and sanitized evidence; restrict access and avoid storing secrets in reports.
Insufficient time to test all supported browsers/devices.Prioritize P0/P1 journeys and the agreed support matrix; document any untested combinations as residual risk.
